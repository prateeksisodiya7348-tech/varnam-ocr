# Interview preparation

Answers you can defend. Every one of them names a trade-off, because that is what
separates "I built a project" from "I understand the system I built".

---

### 1. "Walk me through what happens when I upload an image."

The browser POSTs multipart to `/v1/ocr` on Render. The route enforces a token
bucket, reads the body with a hard 10MB cap, and hands it to `runner`. Runner
validates by **magic bytes** — never the filename — fully decodes the image to
reject truncation, strips EXIF and applies orientation, converts to grayscale and
downscales to a 2000px long edge. Then Otsu binarization, row-projection line
segmentation, reading-order clustering, optional column split. Each line crop is
resized to 32×320 with white padding, run through the CRNN, decoded greedily from
CTC output, and normalized through the shared Devanagari module. Boxes are
inverse-scaled back to original-upload pixels, the result is persisted as JSON,
and a typed response goes back. The UI renders boxes as percentages of the page
size, so they stay aligned at any viewport width.

### 2. "Why not just use Tesseract? It has a Hindi model."

Tesseract's Devanagari output on real scans is genuinely usable, and if the task
were "extract text from clean printed pages tomorrow" I would start there. Three
reasons I did not stop there:

1. **Handwriting.** Tesseract's LSTM models are trained on print; handwriting
   accuracy is close to zero. A trainable CRNN can be fine-tuned on the exact
   distribution you care about.
2. **Output structure.** Tesseract gives words and boxes but not calibrated
   per-line confidence in a form I can drive a review UI from.
3. **Control.** The feedback loop here feeds corrections back into retraining. With
   Tesseract I would be fine-tuning someone else's model through a wrapper.

An honest senior answer: I would **benchmark Tesseract first** and only build this
if it fails the accuracy bar. Building from scratch was also the point of the
exercise, and I say that plainly rather than pretending Tesseract doesn't exist.

### 3. "Why ONNX instead of PyTorch in production?"

Size and cold start. PyTorch CPU wheels are ~900MB installed; onnxruntime is
~40MB. On a 512MB free instance, PyTorch simply does not fit alongside the model
and the web framework. ONNX also gives INT8 quantization for free via
`quantize_dynamic`, which in principle takes the recognizer from ~17MB to ~4MB.
In practice dynamic INT8 rewrites Conv into `ConvInteger`, which onnxruntime's
CPU provider does not implement — so the exporter load-tests the quantized graph
and ships the float model (15.9MB) when it fails. A model that boots beats a
quarter-size model that crashes, and the fallback is verified, not assumed.
(a parity check fails the export at >5% prediction disagreement). PyTorch stays
where it belongs: training.

### 4. "512MB isn't much. How do you stay inside it?"

Four things, each measurable:
- INT8 model instead of float32 (4x smaller weights).
- `intra_op_num_threads=1` — more threads means more memory *and* worse latency on
  one vCPU.
- `enable_cpu_mem_arena=False` — the ORT arena reserves slabs it never returns to
  the OS, which is exactly what triggers the OOM killer.
- Input capped at 2000px long edge, 10MB upload, one page in flight via a
  semaphore.

Peak RSS for an A4 page is roughly 200MB, which leaves headroom for the framework
and the interpreter under 512MB.

### 5. "What's your CER and how did you measure it?"

CER lives in `docs/EVALUATION.md` and is generated by `python -m ml.eval`, never
typed by hand. It reports per-slice macro-averaged CER and WER, plus a
character-confusion table. It measures across the **exact pipeline the API uses**
— `run_page` — so the number is not from a notebook that has since diverged from
production. If a slice has no data it says *not measured*; I do not estimate.

### 6. "Why not a transformer like TrOCR?"

TrOCR is more accurate, and it is ~6x larger and roughly 10x slower on CPU. On one
vCPU with 512MB, a base TrOCR model would put single-page latency well past 10
seconds. The CRNN+CTC design runs a page in hundreds of milliseconds. TrOCR is
documented as the accuracy escape hatch for when a GPU budget exists — that is a
deliberate deferral, not an oversight.

### 7. "Explain CTC decoding."

The CNN reduces the image to a sequence of `T` feature vectors along the
horizontal axis; the head emits a class distribution per step. CTC allows the
alignment to be unknown, so the same label can occupy different step counts. Greedy
decoding takes the argmax per step, collapses consecutive duplicates, then removes
the blank class (index 0). Confidence is the mean probability of the surviving
characters — which is why a line with a deleted character can still look
confident, and why per-character confidence is a roadmap item.

### 8. "Why projection profiles instead of a learned text detector?"

Because Devanagari's shirorekha defeats simple connected-component splitting —
words look like solid rectangles joined by a bar. Ink-density projection along rows
and columns does not depend on connectivity, costs ~2ms, needs no detector model,
and needs no 40MB of weights. It does fail on rotated pages and text over images,
which I state as a limitation and name DBNet as the upgrade. Choosing the boring
deterministic approach and knowing its boundary is the point.

### 9. "How do you guarantee training and serving preprocess identically?"

One shared module: `packages/devanagari_text`. Both `ml/` and `services/api` import
it. It is on `PYTHONPATH` rather than pip-installed, so there is physically one
copy. The normalization rules are the same code path in both places, and the tests
that pin combining marks (`क्ष`, `ज्ञ`, `र्क`, `कँ`, `क़`) run against that single
implementation.

### 10. "What's the hardest Devanagari-specific bug you hit?"

Normalization. The instinct — and what a lot of tutorials do — is to strip
diacritics or "clean" the text before comparison. In Devanagari, the matra *is* the
vowel. `कि` without its i-matra is `क`. Dropping it silently turns every correct
prediction into a wrong one while the pipeline reports success. So there is
deliberately **no** mark-stripping function in the codebase — you cannot call what
does not exist — and the tests pin every combining case.

The second one is the coordinate space: returning boxes in preprocessed
coordinates makes every overlay drift toward the top-left on a downscaled photo,
which looks exactly like a model bug.

### 11. "How does the confidence score work, and can I trust it?"

It is the mean of the softmax probabilities of the decoded (non-blank, non-repeat)
characters. It is *useful* but not calibrated: models are systematically
overconfident, and a line where a character was deleted entirely can still score
high because the deleted step contributes nothing to the mean. Trust it as a
ranking signal for "which lines should a human check first", not as a probability.
Calibration (temperature scaling on a held-out set) is a documented next step.

### 12. "What breaks at 100x traffic?"

In order: (1) the in-process rate limiter, because it is per-instance and resets on
restart — move to Redis; (2) the single inference slot, because one vCPU serializes
everything — move to a queue with autoscaled workers and make the API a thin
enqueue/poll surface (the PDF path already models this); (3) Postgres connection
count, which the Neon pooler handles but will need tuning; (4) `ocr_jobs` table
growth, which needs a retention policy; (5) the layout heuristic, which degrades as
input diversity grows and needs a learned detector.

### 13. "Why is there a fake engine in production code?"

Because the repository must be runnable in one command with no model download, and
because tests need a deterministic fixture. It is safe because it is never silent:
`auto` only selects ONNX when the model file exists, the API reports
`"engine": "fake"` in every response, and startup logs a warning. Silently serving
stub text in production would be unacceptable; doing it *visibly* is a feature.

### 14. "Why separate `OcrJob` from the response schema?"

ORM models and API contracts have different reasons to change. If they are the same
class, adding `client_hash` or `storage_key` to the table silently publishes it.
Keeping Pydantic schemas separate makes leaking an internal column impossible
without an explicit edit.

### 15. "How do you handle a multi-page PDF within a 25-second budget?"

You don't — you refuse to. `POST /v1/ocr/pdf` returns `202` with a job id in under
200ms, and pages are rendered and recognized in a background task, updating the
job row as it goes. The client polls `GET /v1/jobs/{id}`. Blocking would hit the
platform request timeout, which returns an HTML error page the client cannot parse
— so the failure would be invisible. The job row also records a terminal `failed`
state with the error, because a background exception is otherwise unobservable.

### 16. "What did you not finish, and why?"

Listed in `docs/LIMITATIONS.md`, but the top three: (1) no Alembic migrations —
`create_all` is fine for a first deploy and wrong the first time a column changes
on live data; (2) word text is distributed proportionally by box width, not from a
separate word recognizer, so word boundaries are approximate; (3) handwriting
accuracy is weak because public datasets are isolated characters, not connected
writing — that needs data collection, not more model.

Naming these deliberately: a candidate who cannot list their own gaps has not
looked closely at their own system.

### 17. "How would you cut latency in half?"

Measure first: `duration_ms` from the engine versus total request time. Then, in
expected-impact order: (1) cache identical uploads by SHA-256 — the content hash is
already computed for storage; (2) batch line crops through the recognizer instead
of one inference per line, which typically gives 2-3x on CPU due to better SIMD
utilization; (3) skip the angle classifier for already-upright pages; (4) reduce
`MAX_IMAGE_LONG_EDGE` to 1600 and measure the CER cost. Everything after that is
hardware.

### 18. "Is this secure?"

It is *carefully* built, not audited. Uploads are validated by magic bytes, fully
decoded, size- and dimension-capped, EXIF-stripped, and stored under a
content-addressed key so a client filename can never influence a path. Response
headers are hardened, stack traces never reach clients, and internal columns cannot
leak through response schemas. What it does *not* have: authentication on the OCR
endpoint, malware scanning, or protection against feedback poisoning. Those are in
`LIMITATIONS.md` under security, and they are the reason this is a demo and not a
service for other people's identity documents.

### 19. "Why Tailwind v4 and no component library?"

v4 is CSS-first — tokens live in `globals.css` as custom properties and there is no
`tailwind.config.js` to drift out of sync. I skipped a component library because
this UI has six components and a design system would be more code than the product.
If it grew to twenty screens that trade flips, and I would say so.

### 20. "What would you do with two more weeks?"

In order of user impact: (1) collect 500 real phone-photo pages and fine-tune —
that is the distribution that matters and it is currently unrepresented; (2) add
Alembic and an `ocr_jobs` retention policy, because both are debt that grows
silently; (3) implement batched line inference, which is the cheapest real latency
win; (4) review the feedback loop before any of those corrections enter training —
corpus poisoning is a real risk in an unauthenticated system; (5) only then look at
a bigger model.

## The 30-second pitch

> Varnam OCR is a deployed Devanagari OCR system: Next.js on Vercel, FastAPI with an
> INT8 CRNN on Render's free tier. It handles printed and handwritten text, returns
> per-line confidence and pixel-accurate boxes, and exports hOCR so it composes with
> existing document pipelines. The interesting engineering was the constraint work —
> the model cannot run in a serverless function, so inference lives separately; 512MB
> of RAM drives every model and threading choice; and Devanagari's combining marks
> mean the normalization layer has to be built so it is impossible to drop a matra.
> Accuracy is measured per slice by a command, and the limitations are documented
> rather than hidden.
